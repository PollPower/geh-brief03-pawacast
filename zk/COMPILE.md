# Compiling `zk/record.compact`

Target toolchain: Midnight **Compact 0.22** (`compactc 0.30.0`, language 0.22.0,
runtime 0.15.0, ledger 4.0.2). Same compactc build used by
`PollPower/contracts` (EBT v8 + tariff-registry).

Circuit compiles with compactc 0.30.0 (N_MAX 128, proving key 306 MB).
Circuit logic tested on 4 fixtures (valid; too few customers; wrong
commitment; non-zero padding). Not deployed; no on-chain proofs generated
during the sprint.

Do **not** compile this on Windows. `compact` on a Windows PATH is NTFS
compression (`C:\Windows\system32\compact.exe`), not Midnight Compact.
Do **not** deploy the compiled artifact to Midnight Preview without an explicit ask.

On kenya the binary lives at:

```
/home/pollpower/.compact/versions/0.30.0/x86_64-unknown-linux-musl/compactc
```

(`compactc.bin` is the same compiler; deploy scripts on kenya call `compactc.bin`.)

## Exact command

Run from the repo root. `compactc` must be the 0.30.0 build on your `PATH`
(or substitute the absolute path, e.g.
`~/.compact/versions/0.30.0/x86_64-unknown-linux-musl/compactc`).

```
mkdir -p zk/build
compactc zk/record.compact zk/build/
```

Expected: ~10 minutes wall time on an 8-core x86_64 (zkir proving-key
generation dominates — the compactc front-end alone finishes in <5 s;
the long tail is `zkir compile-many build/zkir build/keys`). RAM peaks
around 20 GiB during proving-key setup. No stderr output beyond
`Compiling 1 circuits:`. Build artifacts land under `zk/build/` (gitignored).

## Toolchain pinning

The source declares `pragma language_version >= 0.16 && <= 0.22;` — identical
to the EBT v8 / tariff-registry convention. compactc 0.30.0 speaks language
0.22.0 so the pragma range admits it; older compactc builds inside the range
should also work provided they implement the specific 0.22 syntax used here
(`assert(cond, "msg")`, no top-level `const`, `fold` with struct accumulator,
`persistentHash<Vector<N, Bytes<32>>>`).

If `compactc` isn’t installed, grab it from the Midnight toolchain installer
and verify with `compactc --version` (expect `0.30.0`) and
`compactc --language-version` (expect `0.22.0`).

## Output

`zk/build/` contains:

```
compiler/contract-info.json       circuit + witness manifest
contract/index.d.ts               TypeScript type definitions
contract/index.js                 compiled JS shim (importable)
contract/index.js.map             source map for the JS shim
keys/<circuit>.prover             proving key   (~292 MiB / 306 MB — NOT committed)
keys/<circuit>.verifier           verifying key (~2.1 KiB)
zkir/<circuit>.bzkir              zkir bytecode   (binary)
zkir/<circuit>.zkir               zkir text (human-readable instruction list)
```

A frozen manifest of these artifacts lives at `zk/build-manifest.txt`
(generated by `scripts/gen-build-manifest.sh` after a successful compile).
`zk/build/` itself is gitignored. The 292 MiB prover key is a direct
consequence of the N_MAX=128 vector width.

## Vector width

`N_MAX = 128`. Sites with **n > 128** split into **c = ceil(n/128)** chunks of
**near-equal size** (sizes differ by at most 1). Examples: 130 → 65+65,
300 → 100+100+100. Never “full 128 chunks plus remainder”.

With **n ≥ 25** overall this guarantees every chunk has ≥ 64 customers, so
`K_MIN = 25` holds per chunk. The split lives in
`pawacast/sharing/chunk.py` (`chunk_sizes`, `split_into_chunks`). Each chunk
has its own `salt_k`, `n_k`, `values_k`, and `commitment_k`.

## k-anonymity floor

`record.compact` uses `K_MIN() = 25`, the same floor as
`pawacast/sharing/validate.py` `MIN_CUSTOMERS = 25`. Raised from 10 because
Laplace |noise| at n=10 with a 20 kWh clip is 40% of a typical 5 kWh mean.

## Fixture harness

`zk/run-fixtures.mjs` loads the compiled JS shim and invokes
`prove_published_sum_and_count` once per fixture in `zk/fixtures/`. It checks
that accept/reject matches the fixture’s `expect` field, and for `accept`
fixtures it computes the correct commitment hash on the harness side using
the same `persistentHash` chain as the circuit. It does **not** generate a
real proof.

Prerequisite: `@midnight-ntwrk/compact-runtime@0.15.0` must be resolvable.
On the sprint machine the simplest path is a symlink to the sibling
`PollPower/contracts/tariff-registry/node_modules`:

```
ln -sf ../../contracts/tariff-registry/node_modules zk/node_modules
cd zk
node run-fixtures.mjs
rm zk/node_modules
```

Expected output:

```
=== Fixture results ===
[PASS] n24_should_fail.json: expect=reject outcome=reject commitment=auto-computed err="failed assert: N_BELOW_K_MIN"
[PASS] nonzero_padding.json: expect=reject outcome=reject commitment=auto-computed err="failed assert: PADDING_NONZERO"
[PASS] valid_n25.json: expect=accept outcome=accept commitment=auto-computed
[PASS] wrong_commitment.json: expect=reject outcome=reject commitment=from fixture (ffffffffff…) err="failed assert: COMMITMENT_MISMATCH"
```

The symlink is a convenience, not committed.

## Design: no leakage, commitment binding

The only ledger field is `_version: Uint<8>`, a marker written once as the
constant `1` at the end of every proof call so compactc 0.30.0 classifies
this file as a proof-generating contract. There are no `_proofSum` /
`_proofIdx` scratch cells. No witness-derived value is stored in the ledger.
Witnesses (`privateN`, `privateSalt`, `privateValuesMilliKwh`) are never
`disclose()`’d.

Commitment binding: the circuit recomputes
`H = fold(absorbValue, H(tag_init | salt | n_bytes), values)` with
`persistentHash<Vector<3, Bytes<32>>>` and asserts
`H == commitment` (`COMMITMENT_MISMATCH` if they differ).

Sum and padding live in one `fold` over the 128-wide vector
(`PADDING_NONZERO` when a padding slot is not zero; `SUM_MISMATCH` if the
prefix sum disagrees). Count checks use `N_MISMATCH`, `N_BELOW_K_MIN`,
`N_ABOVE_N_MAX`.
