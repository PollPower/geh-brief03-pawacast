# Compiling `zk/record.compact`

Target toolchain: Midnight **Compact 0.22** (`compactc 0.30.0`, language 0.22.0,
runtime 0.15.0, ledger 4.0.2). Same compactc build used by
`PollPower/contracts` (EBT v8 + tariff-registry).

Not deployed. Preview deploy needs an explicit ask.

## Exact command

Run from the repo root. `compactc` must be the 0.30.0 build on your `PATH`
(or substitute the absolute path, e.g.
`~/.compact/versions/0.30.0/x86_64-unknown-linux-musl/compactc`).

```
mkdir -p zk/build
compactc zk/record.compact zk/build/
```

Expected: ~10 minutes wall time on an 8-core x86_64 (zkir proving-key
generation dominates — the compactc front-end alone finishes in <5 s;
the long tail is `zkir compile-many build/zkir build/keys`). RAM peaks
around 20 GiB during proving-key setup. No stderr output beyond
`Compiling 1 circuits:`. Build artifacts land under `zk/build/`.

## Toolchain pinning

The source declares `pragma language_version >= 0.16 && <= 0.22;` — identical
to the EBT v8 / tariff-registry convention. compactc 0.30.0 speaks language
0.22.0 so the pragma range admits it; older compactc builds inside the range
should also work provided they implement the specific 0.22 syntax used here
(`assert(cond, "msg")`, no top-level `const`, `fold` with struct accumulator,
`persistentHash<Vector<N, Bytes<32>>>`).

If `compactc` isn’t installed, grab it from the Midnight toolchain installer
and verify with `compactc --version` (expect `0.30.0`) and
`compactc --language-version` (expect `0.22.0`).

## Output

`zk/build/` contains:

```
compiler/contract-info.json       circuit + witness manifest
contract/index.d.ts               TypeScript type definitions
contract/index.js                 compiled JS shim (importable)
contract/index.js.map             source map for the JS shim
keys/<circuit>.prover             proving key   (~292 MiB — NOT committed)
keys/<circuit>.verifier           verifying key (~2.1 KiB)
zkir/<circuit>.bzkir              zkir bytecode   (binary)
zkir/<circuit>.zkir               zkir text (human-readable instruction list)
```

A frozen manifest of these artifacts lives at `zk/build-manifest.txt`
(generated by `scripts/gen-build-manifest.sh` after a successful compile).
`zk/build/` itself is gitignored. The 292 MiB prover key is a direct
consequence of the N_MAX=128 vector width — ~128 persistentHash fold steps
unroll into the proving system; the key size scales roughly linearly in
N_MAX.

## Fixture harness

`zk/run-fixtures.mjs` is a minimal offline harness: it loads the compiled JS
shim and invokes `prove_published_sum_and_count` once per fixture in
`zk/fixtures/`, with the fixture’s witness values. It checks that the
circuit’s accept/reject outcome matches the fixture’s `expect` field, and
for `accept` fixtures it computes the correct commitment hash on the harness
side using the same `persistentHash` chain as the circuit (little-endian
`convertFieldToBytes` for `Uint<32>` → `Bytes<32>`, see
`@midnight-ntwrk/compact-runtime/dist/casts.js`). It does **not** generate a
real proof — it exercises the circuit’s assert/revert logic end-to-end
against the compiled TS/JS shim and the compact runtime.

Prerequisite: `@midnight-ntwrk/compact-runtime@0.15.0` must be resolvable.
On the sprint machine the simplest path is a symlink to the sibling
`PollPower/contracts/tariff-registry/node_modules`:

```
ln -sf ../../contracts/tariff-registry/node_modules zk/node_modules
cd zk
node run-fixtures.mjs
rm zk/node_modules
```

Expected output:

```
=== Fixture results ===
[PASS] n24_should_fail.json: expect=reject outcome=reject commitment=auto-computed err="failed assert: N_BELOW_K_MIN"
[PASS] nonzero_padding.json: expect=reject outcome=reject commitment=auto-computed err="failed assert: PADDING_NONZERO"
[PASS] valid_n25.json: expect=accept outcome=accept commitment=auto-computed
[PASS] wrong_commitment.json: expect=reject outcome=reject commitment=from fixture (ffffffffff…) err="failed assert: COMMITMENT_MISMATCH"
```

The symlink is a convenience, not committed. If you’d rather have a proper
`package.json` in `zk/`, add one with a single dependency on
`@midnight-ntwrk/compact-runtime@0.15.0` and run `npm install` there.

## k-anonymity floor

`record.compact` uses `K_MIN() = 25`. This is **higher** than
`pawacast/sharing/validate.py` `MIN_CUSTOMERS = 10`. The two are intentionally
unaligned at this commit — the circuit encodes the sprint policy; `validate.py`
still reflects the pre-sprint design. Any reconciliation (either lifting the
Python floor to 25, or lowering the circuit floor back to 10) is a separate
repo change and is not performed here.

## Vector width (N_MAX) and chunking

`N_MAX = 128`. The sprint target was 256; a trial compile at N_MAX=256 on an
8-core x86_64 held `zkir compile-many` at 99 % CPU with RSS climbing past 27
GiB and 1.3 GiB swap after ~23 minutes with no artifacts yet written, so we
backed off to 128. At 128 the compile completes in ~10 minutes with ~20 GiB
peak RSS and emits a 292 MiB proving key.

**Chunking for larger sites.** When a site has more than 128 active customers,
the operator chunks the record into `⌈n_total / 128⌉` sub-records, each with
its own:

- `salt_k` — fresh blinding salt per chunk
- `n_k` — customer count in the chunk (≥ `K_MIN`)
- `values_k` — length-128 vector, zero-padded past `n_k`
- `commitment_k = chainedHash(salt_k, n_k, values_k)` published alongside the
  parent EBT settlement entry

Each chunk produces its own ZK proof against this circuit. The published
site-month record then publishes `sum = Σ sum_k` and `n = Σ n_k`
alongside the per-chunk commitments. The `k ≥ K_MIN` guard applies
**per chunk**, which is a strictly stronger privacy guarantee than aggregate
`k ≥ K_MIN` since every published chunk independently satisfies the k-anonymity
floor. Verifiers check each chunk’s proof against its chunk commitment, then
sum the published per-chunk `n` and `sum_milliKwh` on the record-aggregator
side (off-chain).

Raising `N_MAX` beyond 128 is a trade between proving-key size (linear in
N_MAX), compile time (super-linear), and prover compute. 128 is a reasonable
compromise for a 100-household pilot site and keeps the proving key under
300 MiB.

## Design: no leakage, commitment binding

The circuit upholds three ZK invariants that previous iterations did not:

1. **No ledger scratch.** The only ledger field is `_version: Uint<8>`, a
   marker that is written once (as the constant `1`) at the end of every
   proof call. It exists solely to classify this file as a proof-generating
   contract (compactc 0.30.0 skips zkir and proving-key generation for
   stateless circuits — a bare `witness → assert → return` shape emits only
   the TS shim). No witness-derived value is ever stored in the ledger.

2. **No `disclose()` of witness values.** `privateN`, `privateSalt`, and
   `privateValuesMilliKwh` are read into local `const` bindings and compared
   against public inputs via `assert(a == b, "LABEL")`. Those comparisons
   verify equality inside the proof without copying the witness to the
   public transcript — the proof’s validity is the only public claim. Grep
   the generated JS: zero `disclose(` call sites in `zk/build/contract/index.js`.

3. **Commitment binding.** The circuit recomputes
   `H = persistentHash<Vec<3,Bytes<32>>>([tag_absorb, …])` folded over
   `(tag_init | salt | n_bytes | v_0 | v_1 | … | v_{N_MAX-1})` and asserts
   `H == commitment`. The operator pre-publishes `commitment` alongside the
   EBT settlement entry (Tier 1 binding). A prover can’t swap out the
   witness without changing the recomputed hash, so the proof is pinned
   to a specific `(salt, n, values)` tuple — grinding attacks against the
   published sum/count require either the salt (unknown to a public
   attacker) or breaking persistentHash.

Accumulation uses `fold` with a struct accumulator `{sum: Uint<64>,
remaining: Uint<32>}` and a one-pass reducer that:
- while `remaining > 0`: adds `v` to `sum`, decrements `remaining`;
- once `remaining == 0`: asserts `v == 0` (padding guard, PADDING_NONZERO).

A separate `fold` runs over the same values vector with a `Bytes<32>` running
hash, chaining `persistentHash<Vector<3, Bytes<32>>>([tag, prevHash, v_bytes])`
per element.

## Changes from the Compact 0.18 scaffold → 0.22 v2

### 0.22 syntax conversions (same as v1)

- `pragma language_version >= 0.16 && <= 0.22`
- `assert(cond, "LABEL")` function-call form (not statement form)
- No top-level `const`; use `pure circuit NAME(): T { return VAL; }`
- No `let mut`; use fold reducers or ledger scratch
- Circuit return type `[]` (unit); the circuit relies on asserts for truth
- Explicit narrowing casts on arithmetic: `(a + b) as Uint<64>`

### v2 design fixes (this commit)

- Removed ledger scratch cells (`_proofSum`, `_proofIdx` → gone).
- Added `_version: Uint<8>` as the sole ledger field (proof-generation
  marker only; no witness leakage path).
- Replaced the in-circuit for-loop with `fold(sumAndCheckPad, init, values)`
  using a struct accumulator — all accumulation lives on the fold stack,
  not in ledger.
- Added commitment binding: new witness `privateSalt(): Bytes<32>`; new
  public arg `commitment: Bytes<32>`; chained-hash fold using
  `persistentHash<Vector<3, Bytes<32>>>`.
- Raised `N_MAX` 32 → 128 (256 was too heavy, see §Vector width).
- Removed every `disclose()` call site.
- Four new fixtures covering the full assert surface: accept, k-min reject,
  wrong-commitment reject, nonzero-padding reject.
